Standard Hybride Humain & IA

Charte de Développement Logiciel

Directives universelles, règles d'encodage et consignes d'exécution strictes pour les agents IA.

1. Introduction & Objectifs

Cette charte définit les standards de qualité, de maintenabilité, de robustesse et de sécurité exigés pour tout code produit au sein du projet. Tout code soumis (par un humain ou une IA) doit respecter rigoureusement ces directives.

2. Principes Fondamentaux de Conception

  • SOLID : Respect strict des 5 principes de conception orientée objet.
  • DRY (Don't Repeat Yourself) : Factorisation de la logique métier dans des composants réutilisables.
  • KISS (Keep It Simple, Stupid) : Privilégier la solution la plus simple, lisible et directe, sans sur-ingénierie.
  • YAGNI (You Aren't Gonna Need It) : Pas de fonctionnalités anticipées non requises.

3. Clean Code, Nommage et Gestion des Caractères

  • Nommage explicite : Les noms de variables, fonctions et classes doivent révéler leur intention de manière univoque.
  • Fonctions courtes : Une fonction ne fait qu'une seule chose et tient idéalement sur un écran (moins de 30 lignes).
  • Constantes : Bannir les "magic numbers" et chaînes en dur.

Règle Critique : Sécurité des Caractères et Encodage

Pour prévenir toute erreur d'encodage (UTF-8), de compilation ou de parsing :

  • Pas d'accents dans le code source : Les identifiants (variables, fonctions, classes, noms de fichiers, tables, colonnes) doivent être rédigés en anglais technique sans accents ni caractères diacritiques (ex: utiliser user_total au lieu de montant_total_utilisateurs si l'on souhaite l'anglais, ou total_clients sans accent).
  • Bannissement des icônes et émojis : Interdiction formelle d'inclure des émojis ou des icônes Unicode superflues dans le code source, les commentaires techniques ou les logs, sauf s'ils font explicitement partie du texte UI destiné aux utilisateurs finaux.
  • Caractères spéciaux : Éviter les caractères de contrôle invisibles, les guillemets typographiques typographiques (“ ”, ‘ ’) au profit des guillemets droits standard (" ", ' ').

4. Documentation et Commentaires

  • Le code parle de lui-même : Les commentaires expliquent le pourquoi (contexte, choix architecturaux), jamais le ce que fait le code.
  • Langue des commentaires : Rédaction des commentaires de code en anglais technique pour garantir l'uniformité internationale.
  • Documentation des API/Fonctions : Utilisation systématique des standards (JSDoc, Docstrings).

5. Sécurité et Gestion des Erreurs

  • Validation des entrées : Validation et assainissement systématiques de toutes les données externes.
  • Gestion des erreurs : Interception propre, logs contextuels et remontées d'erreurs sécurisées.
  • Secrets : Usage exclusif de variables d'environnement (zéro secret hardcodé).

6. Instructions Système Dédiées aux Développeurs IA (System Prompt)

Ce bloc est spécifiquement formaté pour être injecté dans les instructions de votre agent IA ou de votre fichier .cursorrules.

Règle IA 1 : Interdiction des Placeholders et du Code Incomplet

L'IA ne doit jamais utiliser de commentaires du type // TODO: implement later, // ... existing code ... masquant de la logique, ou de fonctions vides. Tout code généré doit être complet, fonctionnel et testable immédiatement.

Règle IA 2 : Intégrité Stricte du Jeu de Caractères

L'IA doit s'interdire d'insérer des accents dans le code source (noms de variables, fonctions, clés JSON, attributs de base de données) et s'abstenir d'inclure des émojis ou caractères spéciaux non indispensables à la syntaxe ou aux textes utilisateurs.

Règle IA 3 : Auto-Validation (Self-Correction)

Avant de délivrer sa réponse, l'IA doit s'auto-évaluer sur :

  • L'absence totale d'accents ou d'émojis parasites dans la syntaxe du code.
  • L'absence de failles de sécurité courantes (OWASP Top 10).
  • La présence de la documentation JSDoc / Docstring sur toutes les nouvelles fonctions publiques.
