⚙️ 1. Prérequis Systèmes & Guide d'Installation

Afin de faire tourner le pipeline complet avec ses agents IA locaux, ses bases vectorielles et le moteur de test de sécurité blockchain, la machine hôte doit disposer des outils suivants :

1.1. Matériel & Systèmes d'Exploitation Recommandés

  • OS : Ubuntu 22.04 LTS / macOS Sonoma / Windows avec WSL2 (Ubuntu).
  • RAM : 16 Go minimum (32 Go recommandés pour exécuter Ollama et Anvil simultanément).
  • Stockage : 50 Go d'espace libre (images Docker, cache Foundry et modèles LLM).

🎯 2. Description Fonctionnelle, Workflow Auto-Débogage & Rôle du Pilote (HITL)

Le pipeline agit comme une équipe d'ingénierie autonome sous le contrôle d'un Tech Lead humain. Une caractéristique fondamentale du système est sa boucle de test et d'auto-débogage autonome pré-validation : aucun code n'est présenté à l'humain s'il n'a pas préalablement réussi 100 % de ses tests unitaires, d'invariants et d'audits de sécurité.

🔄 Déroulement Strict du Workflow de Développement :
1. Génération : L'agent spécialisé produit le code Solidity ou TypeScript.
2. Compilation & Tests Unitaires : Le système exécute automatiquement forge test.
3. Bouclier de Sécurité Multi-Couches : Slither (AST), Fuzzing (Foundry), Threat Simulator (Anvil) et Halmos (Preuve Formelle) auditent le code.
4. Boucle d'Auto-Correction (En cas d'échec) : Si une erreur de compilation ou une vulnérabilité est détectée, le système intercepte la sortie d'erreur, la réinjecte au LLM sous forme de prompt correctif et relance les tests. Cette boucle s'exécute jusqu'à 3 fois de manière autonome.
5. Présentation à l'Humain (HITL) : Ce n'est qu'une fois le code totalement propre et validé par les outils déterministes qu'une notification est envoyée au Dashboard avec le diff et le lien Gist pour validation humaine.

Rôles des Acteurs Métier

  • L'Agent Architecte : Analyse le besoin, génère le DAG de tâches et identifie les compétences requises.
  • La Dev Squad (Agents de Dev) : Rédige le code, les tests unitaires (*.t.sol) et les scripts d'invariants.
  • Le Circuit Breaker & Auto-Debugger : Gère les tentatives de correction automatique (max 3 itérations) avant d'alerter si un blocage persiste.
  • Le Pilote Humain (Tech Lead) : Inspecte le code déjà certifié sur le Dashboard, visualise les diffs et donne le feu vert pour le commit final sur Git.

🛡️ 3. Bouclier Anti-Hallucinations & Mitigation des Effets Indésirables IA

Les modèles de langage (LLM) présentent des risques connus lorsqu'ils génèrent du code critique Web3. Le pipeline embarque des mécanismes de protection stricts à chaque étape :

Effet Indésirable / BiaisSymptôme & Risque MétierMécanisme de Protection Technique
Hallucination de Syntaxe / Dépendances Importation de bibliothèques inexistantes ou syntaxe Solidity obsolète. Boucle de Compilation Déterministe : Tout code est immédiatement soumis à forge build. L'AST exact et l'erreur du compilateur sont réinjectés à l'agent sans passer par une auto-évaluation du LLM.
Invention d'API / Fonctions Appel de méthodes absentes des standards ERC. RAG Vectoriel Strict (ChromaDB) : Le prompt est ancré (grounded) uniquement sur les interfaces vérifiées d'OpenZeppelin v5 stockées en vector store. Interdiction d'inventer des signatures.
Dérive de Contexte (Scope Drift) L'agent modifie des parties du contrat non demandées ou oublie des contraintes architecturales. Stateless Execution & Context Pinning : L'état réside dans PostgreSQL. Chaque requête est exécutée dans un contexte propre réinjectant le System Prompt invariant de la tâche DAG en cours.
Boucle Infinie de Refactoring L'agent corrige un bug mais en introduit un autre, tournant en boucle indéfiniment. Circuit Breaker (Disjoncteur) : Plafond strict à 3 essais de correction automatique. En cas de dépassement, la tâche passe en statut WAITING_HUMAN_VALIDATION / CIRCUIT_BROKEN avec le journal complet des erreurs.
Opacité du Raisonnement Impossibilité d'expliquer pourquoi l'agent a choisi une structure de données plutôt qu'une autre. Audit Trail JSON : Chaque décision de l'agent est enregistrée avec sa promesse (prompt), sa réponse brute et la trace de compilation associée dans la table execution_logs.
Auto-Complaisance IA L'agent affirme que le code est sécurisé sans l'avoir réellement testé. Séparation Étanche Dev vs Audit : L'évaluation est réalisée par des sous-processus système (Slither, Halmos, Anvil) externes et déterministes. Le LLM ne juge jamais son propre code.

🧬 4. Moteur d'Acquisition & Injection Dynamique de Compétences Expertes (BaseSkill)

Le pipeline n'utilise pas d'agents figés. L'Agent Architecte conçoit des agents sur-mesure pour chaque projet en leur assemblant des compétences expertes (BaseSkill) instanciées à chaud.

4.1. Anatomie d'une Compétence Experte (BaseSkill)

Une compétence est un module autonome comprenant 3 composants indissociables :

  • Prompt Template & Rules : Directives d'expertise métier, anti-patterns à éviter et exemples concrets (few-shot prompts).
  • Tooling Executable : Wrapper Python encapsulant les appels système ou CLI (ex: compilation forge, appels RPC, requêtes Slither).
  • Schéma Pydantic : Contrat de données strict imposant la structure des paramètres d'entrée et de sortie.

4.2. Processus Pas à Pas d'Acquisition Dynamique

Étape A : Cartographie du Projet par l'Architecte
Lors de l'analyse du project_config.yaml, l'Agent Architecte décompose le projet en tâches DAG et liste les compétences requises (ex: ERC20VaultSkill, ChainlinkOracleSkill, HalmosProofSkill).
Étape B : Interrogation du Registre (SkillRegistry)
Le système interroge la base vectorielle ChromaDB et PostgreSQL. Si la compétence existe déjà, elle est directement chargée.
Étape C : Synthèse Dynamique à Chaud (Si Compétence Inexistante)
Si une compétence métier requise est absente du catalogue :
1. L'Architecte déclenche un méta-prompt de création de compétence.
2. Il recherche la documentation officielle de référence via RAG (ex: documentation Chainlink CCIP).
3. Il génère la classe Python héritant de BaseSkill, avec son modèle Pydantic et ses règles de prompt.
4. La compétence est compilée, validée et enregistrée dans le SkillRegistry pour réutilisation ultérieure.
Étape D : Assemblage Runtime par l'AgentFactory
L'AgentFactory prend un AgentTemplate vierge, lui injecte les compétences requises et instancie l'agent final prêt à exécuter sa mission dans le DAG.

🛡️ 6. Shielding Sécurité Multi-Couches (Anti-Attaques Web3)

Le bouclier de sécurité exécute 4 niveaux d'analyse déterministes. Tout échec déclenche une réinjection immédiate de la trace dans la boucle d'auto-débogage de l'agent.

NiveauMoteur / OutillageVecteurs d'Attaques CiblésAction en cas d'Echec
Niveau 1 Slither / Aderyn Réentrance basique, variables non initialisées, re-entrancy d'état, shadowing. Interception de l'AST Slither -> Auto-correction Agent.
Niveau 2 Foundry / Echidna Fuzzing Violations d'invariants métier, erreurs d'arrondi, overflow d'état. Extraction du contre-exemple de fuzzing -> Auto-correction Agent.
Niveau 3 Anvil Threat Simulator Flash Loans, manipulation d'oracles Uniswap/Chainlink, MEV, front-running. Capture de la trace d'attaque Anvil -> Auto-correction Agent.
Niveau 4 Halmos Symbolic Prover Insolvabilité du coffre, brèche de logique métier multi-fonctions. Extraction du contre-exemple mathématique Z3 -> Auto-correction Agent.

from sqlalchemy.orm import declarative_base, relationship

from src.db.database import Base

class ProjectStatus(str, enum.Enum):
    CREATED = "CREATED"
    IN_PROGRESS = "IN_PROGRESS"
    COMPLETED = "COMPLETED"
    FAILED = "FAILED"

class ProjectModel(Base):
    __tablename__ = "projects"
    id = Column(String, primary_key=True)
    name = Column(String, nullable=False)
    status = Column(Enum(ProjectStatus), default=ProjectStatus.CREATED)
    spec_yaml = Column(Text, nullable=False)
    created_at = Column(DateTime, default=datetime.datetime.utcnow)
    tasks = relationship("TaskModel", back_populates="project")

    def to_dict(self) -> dict:

            self.completed_tasks.add(task.get("id"))
        return results

    async def _execute_node(self, task: Dict) -> Dict:
        agent_id = task.get("agent_id")
        if agent_id not in self.agents:
            raise TaskExecutionError(task_id=task.get("id", "unknown"), message=f"Agent '{agent_id}' not found")
        agent = self.agents[agent_id]
        return await agent.execute_task(task)

    def _resolve_order(self) -> List[Dict]:
        graph = {t.get("id"): set(t.get("depends_on", [])) for t in self.tasks}
        in_degree = {t.get("id"): len(graph[t.get("id")]) for t in self.tasks}
        queue = deque([t for t in self.tasks if in_degree[t.get("id")] == 0])
        result = []
        while queue:
            node = queue.popleft()
            result.append(node)
            for other in self.tasks:
                if node.get("id") in graph[other.get("id")]:
                    in_degree[other.get("id")] -= 1
                    if in_degree[other.get("id")] == 0:
                        queue.append(other)
        if len(result) != len(self.tasks):
            raise ValueError("Cycle detected in DAG")
        return result

    def _is_ready(self, task: Dict) -> bool:
        return all(dep in self.completed_tasks for dep in task.get("depends_on", []))

class ConnectionManager:
    def __init__(self):
        self.active_connections: List[WebSocket] = []

    async def connect(self, websocket: WebSocket) -> None:
        await websocket.accept()
        self.active_connections.append(websocket)

    async def broadcast_status(self, message: dict) -> None:
        for connection in self.active_connections:
            try:
                await connection.send_json(message)
            except Exception:
                pass

        if websocket in self.active_connections:
            self.active_connections.remove(websocket)
